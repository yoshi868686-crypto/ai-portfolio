Case 02

音声メモ1本から、記事4種類までを通す

記事 パイプライン 文字起こし 2026.08

課題

録音は溜まるのに記事にならない。理由ははっきりしていて、文字起こしから記事にするまでの工程が長すぎるからです。聞き直して、要点を拾って、裏を取って、構成を決めて、書いて、SNS用に縮める。どこかで止まると、そこから先は永久に進みません。

設計

1本の長い手順書にせず、4つの独立した工程に割りました。途中で止まっても、次はその工程から再開できます。

各工程は入力フォルダと出力フォルダだけで繋がっています。前の工程の成果物がそこにあれば動く。会話の文脈は引き継ぎません。

詰まった点

1. 裏づけ資料が0件だと、記事が空回りする

文字起こしには検証できる数値がたくさん出てくるのに、参照する資料が1つも無い状態で記事化させると、話者の言ったことをそのまま書くだけになります。そこで先に Web で裏を取り、その出典を記事フォルダに残す方針に変えました。次回以降そのフォルダを再利用できます。実際、話者が「6〜7割」と言っていたシェアが、実際はもっと高いことが照合で分かりました。

2. 自動文字起こしの誤認識が、そのまま記事に入る

固有名詞が激しく崩れます。専門用語が同音の別語に化ける、人名が別人になる、地名が実在しない語になる。誤った補正は、崩れたままの誤変換よりたちが悪い——読み手が気づけないからです。

採った方針は3つ。文脈から一意に定まるものだけ補正する。迷ったら直さず注記する。本文では正しい表記に統一したうえで、根拠と確信度を末尾の節にまとめる。記事の冒頭にも、自動文字起こしを基にしている旨のお断りを必ず入れます。

3. 注記が加工の途中で消える

元記事に「一次ソース未確認」と書いてあっても、SNS用に140字へ縮める過程で真っ先に落ちます。数字を扱う以上そこは消せないので、全加工物に注記を継承させるルールを入れました。140字に入りきらない場合は、リプライ用の注記文を別に添えさせています。

4. 画像生成は課金するので、先に検算する

生成は1枚ごとに課金され、途中で止めても戻りません。だから API を叩く前に設定ファイルを検証するスクリプトを挟みました。同名が2つあると同じファイルに上書きされ、払ったのに1枚しか残らないためです。

検証

文字数は目視で数えません。実測スクリプトの出力だけを判定に使います。

加工物実測判定
やさしい解説3,459 字OK
画像生成プロンプト5枚分共通スタイル定義 + 各比率指定
SNS 140字本命 132 字 / 差し替え4案 115〜122 字OK
SNS 2000字1,917 字上限に余裕あり

SNS用の文字数は、通常の文字数とは数え方そのものが違います（全角1文字＝2、半角＝0.5、URLは一律で固定値）。専用の計算を実装して、そちらで判定しています。

結果

対談音声1本から 7,725 字の解説記事まで到達しました。本文だけで約6,300字、うち改行294個・スペース61個。Web からのコピペ由来の見えない空白が混ざっていないことも確認済みです。

学んだこと — 工程を割ると、止まった場所から再開できる。

一本の長い自動化にすると、途中で失敗したとき最初からやり直しになります。フォルダを挟んで工程を切っておくと、失敗した工程だけ直せる。そして各工程が短いぶん、何が起きたか読めます。全部を1回で通す入口も用意してありますが、それは中で同じ3つを順に呼んでいるだけです。
